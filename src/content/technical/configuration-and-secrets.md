## Where settings live

| Place | Holds | Who can see |
|---|---|---|
| **GitHub → repository → Settings → Secrets and variables → Actions** | The **source of truth** for production settings. The backend workflow writes them into the server’s `.env` on every deploy; the frontend workflow builds them into the app | GitHub repository admins |
| `backend/.env` on the OCI server | Generated by the deploy. **Edits by hand are overwritten** on the next deploy | Anyone with SSH access |
| `backend/env.example`, frontend `.env.local` | Templates and local development only | Developers |
| **Church password manager** | Account logins for each service (Stripe, Square, Supabase…) | The two designated administrators |

:::danger Never put a secret in this guide, in email, in chat, or in the code
This guide is published on the internet. Settings are listed here **by name only**.
:::

## Backend settings (GitHub secrets)

| Setting | Purpose |
|---|---|
| `DATABASE_URL` | Connection to the production Supabase database. The most sensitive setting |
| `FIREBASE_SERVICE_ACCOUNT_BASE64` | Lets the server verify sign-ins (Firebase Admin) |
| `FRONTEND_URL` | Allowed website address (CORS) |
| `NODE_ENV`, `PORT` | Must be `production` and the port nginx forwards to |
| `JWT_SECRET` | Legacy token signing |
| `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` | Stripe payments and the donation webhook signature |
| `STRIPE_MERCH_WEBHOOK_SECRET`, `MERCH_TAX_MODE`, `MERCH_TAX_RATE_BPS`, `MERCH_FALLBACK_EMAIL` | Merchandise checkout |
| `SQUARE_ENV`, `SQUARE_ACCESS_TOKEN`, `SQUARE_WEBHOOK_SIGNATURE_KEY`, `SQUARE_WEBHOOK_URL` | Square reader payments |
| `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`, `GMAIL_USER` | Reading Zelle emails from the church Gmail |
| `ZELLE_SYNC_ENABLED` | Turns the Zelle email reader on |
| `MAILER_GMAIL_*` | Sending emails (e.g. meeting minutes, statements) |
| `GALLERY_DRIVE_*`, `REACT_APP_GALLERY_FOLDER_ID` | Photo gallery from Google Drive (also the fallback for the ledger export) |
| `LEDGER_SHEETS_*` | The Google Sheets ledger backup (enabled flag, environment, folder, spreadsheet, schedule defaults, Google credentials) |
| `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER`, `TWILIO_DRY_RUN` | SMS and voicemail. `TWILIO_DRY_RUN=true` sends nothing |
| `YOUTUBE_API_KEY`, `YOUTUBE_CHANNEL_ID`, `YOUTUBE_SPIRITUAL_CHANNEL_ID`, `OVERRIDE_YOUTUBE_LIVE_FLAG` | Live-stream banner |
| `START_RECEIPT_NUMBER` | Where the skipped-receipt check starts counting |
| `CHURCH_EIN` | The church’s tax ID printed on statements |
| `SENTRY_DSN` | Error reporting |
| Deploy access: `OCI_HOST`, `OCI_USERNAME`, `OCI_SSH_KEY` | How GitHub reaches the server |

Settings in `env.example` but **not** passed by the deploy workflow, such as `ZELLE_GMAIL_CREATE_ENABLED` and `DEPOSIT_CONTROL_START`, take their built-in defaults in production. `ZELLE_GMAIL_CREATE_ENABLED` must stay **off**; see the Zelle design notes in the application repository (`backend/ZELLE_INGESTION.md`).

## Frontend settings (GitHub secrets, built into the app)

`REACT_APP_API_URL`, `REACT_APP_STRIPE_PUBLISHABLE_KEY` (must be a **live** key), `REACT_APP_FIREBASE_*` (seven values from the Firebase project), `REACT_APP_RECAPTCHA_SITE_KEY`, `REACT_APP_ENABLE_PHONE_AUTH` / `REACT_APP_ENABLE_EMAIL_AUTH`, `REACT_APP_YOUTUBE_SPIRITUAL_CHANNEL_ID`, `REACT_APP_GALLERY_FOLDER_ID`, `REACT_APP_UMAMI_SRC` / `_WEBSITE_ID` / `_SHARE_URL`, `REACT_APP_SENTRY_DSN`, and optionally `REACT_APP_HELP_URL` (where the **Help** link points; by default this guide’s GitHub Pages address). Also `FIREBASE_TOKEN` for deploying.

These values are visible to anyone using the website (they are in the app’s code). That is normal for “publishable” keys; never put a **secret** key in a `REACT_APP_` setting.

## Changing or rotating a setting

:::steps
1. Create the new value in the outside service, e.g. a new Stripe webhook secret or a Gmail refresh token. See [Integrations](#/continuity/integrations).
2. GitHub → Settings → Secrets → update the secret.
3. **Actions → Deploy Backend (or Firebase) → Run workflow** on `main`.
4. Test the feature it controls.
5. Revoke the old value in the outside service.
6. Record in the password manager when it was rotated and by whom.
:::

:::warning Demo mode must never reach production
The backend has a **demo mode** that bypasses sign-in for walkthroughs and tests (`ENABLE_DEMO_MODE`). The server refuses to start if it is turned on in production. Never add it to GitHub secrets.
:::
